# EnjoyRead `app.html` 結構分離建議

> 適用檔案：[enjoyread/app.html](../enjoyread/app.html)（單檔內含大量 `<style>` 與 `<script>`）  
> 目的：讓專案結構更清楚、日後較容易維護，而不必一次性引入重型建置。

---

## 1. 為什麼會覺得「太長」

目前 `app.html` 類型常見的痛點是：

- **樣式**：整頁刻在 `<style>` 裡，捲動與搜尋都費力。
- **邏輯**：整頁刻在 `<script>` 裡，與標記混在一起時，很難快速對照「這段 UI 對應哪段行為」。

因此「結構更清晰」往往不是先拆 **多個 HTML 檔**，而是先把 **CSS／JS 與 HTML 骨架分離**，通常就能把單檔長度砍掉大半。

---

## 2. 建議順序（由易到難）

### 階段 A：抽出 CSS（優先）

- 將 `<style>…</style>` 內容移到例如 `enjoyread/app.css`（或 `enjoyread/css/app.css`）。
- 在 `app.html` 的 `<head>` 用 `<link rel="stylesheet" href="app.css?v=1">` 引用。
- 好處：零建置工具、靜態託管（Pages／Workers Sites）照常可用；`?v=` 可做快取版本。

### 階段 B：抽出 JS

- 將 `<script>…</script>` 移到例如 `enjoyread/app.js`。
- 在 `</body>` 前 `<script src="app.js?v=1" defer></script>`（視依賴關係決定是否要 `defer`／`type="module"`）。
- 若檔案仍過大：再拆成多個 `js` 檔，以 `type="module"` + `import` 模組化（仍可不使用打包器，但需注意瀏覽器與路徑）。

### 階段 C：若仍要「HTML 本體也拆開」再評估建置或載入策略

「多個 `.html` 檔」在**純靜態、無伺服器模版**下，並沒有一種十全十美的瀏覽器原生組裝方式。常見選項：

| 作法 | 適合情境 | 注意 |
|------|----------|------|
| **建置工具**（Vite、esbuild 等） | 希望片段化模版、長期元件化 | 需 `npm` 與建置流程 |
| **`fetch` 載入 `.html` 片段** | 有固定 origin（同源）的小專案 | `file://` 常不可用；宜用本機伺服器驗證 |
| **`iframe` 嵌入** | 極少用於主版面 | 高度、無障礙、與父頁互動較麻煩 |
| **伺服器側 include**（SSI 等） | 有可自行設定的伺服器 | 不是單純「開 HTML 就上線」 |

**務實結論：**多數情境下 **階段 A + B** 已能解決「檔案太長／結構不清」的主角問題；是否要走到 **階段 C** 可看團隊是否願意加輕量建置。

---

## 3. 與部署的相容性（Cloudflare Pages 等）

- **只拆 `app.css` / `app.js`**：通常是相對路徑，只要不改對外入口 URL、路徑層級正確即可。
- 若將來改 **Vite**：輸出目錄要與現在專案對外路徑一致（或由 CI 發佈設定對齊），避免公開網址 404。

---

## 4. 建議的下一步決策問題（執行前可再想一下）

1. **是否接受引入 `npm` + Vite（或類似）？**  
   - **否** → 以 **外链 CSS／JS + 視需要 `type="module"`** 為主。  
   - **是** → 可規劃「HTML 片段／元件化」並與資產管線對齊。

2. **`app.html` 是否為唯一使用者入口？**  
   - 若是，拆分後仍以同一檔名作入口最保險，避免對外書籤與文件鏈結失效。

---

## 5. 參考路徑（建議拆分後約略長相）

```
enjoyread/
  app.html      ← 縮短的骨架：head／主要區塊容器／link／script src
  app.css       ← 自原 inline style 遷移
  app.js        ← 自原 inline script 遷移
```

（目錄名稱可依你們習慣改成 `styles/`、`scripts/`，但要一次改齊 `<link>` / `<script src>`。）
